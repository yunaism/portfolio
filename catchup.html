CatchUp

A study-notes pipeline that parses a PDF, a Jupyter notebook and screenshots into one block schema, writes section-based notes, answers questions with citations, and links the same concept across documents.

RoleSolodesign, build and evaluation
Tests337mostly mocked

problem

Material for one topic is often spread across formats: a lecture PDF, a notebook with the code, and screenshots. Summarising each document on its own produces notes that never connect the same concept across them.

what I built

  1. Parsers

    PDFs go through Docling's DocumentConverter and notebooks through nbformat. Images go through a VLM parser that makes two calls per image and sorts images into 6 classes.

  2. Unified block schema

    All three parsers write the same block format, so everything downstream works the same way whatever the source document was.

  3. Notes

    Section-based note generation over the blocks, plus a chatbot for editing the generated notes.

  4. RAG Q&A

    Answers carry inline citations to the source blocks. Each retrieved block is expanded with ±2 neighbouring blocks for context. Retrieval uses OpenAI embeddings and ChromaDB directly, without LangChain.

  5. Figures and export

    Figures are extracted from PDFs and enriched with a VLM description. Notes export to Markdown, PDF and DOCX.

  6. Cross-document concept linking

    Concepts are linked first by exact canonical-name match, then by embedding similarity of at least 0.75, with an LLM labelling the relation between the two concepts.

Calls are traced in Langfuse. The 337 tests are mostly mocked. A Docker setup for Hugging Face Spaces exists; the current Space build predates concept linking.

evaluation

Gains smaller than the noise

Single runsper configuration

When I re-checked the results, the same baseline configuration scored differently from round to round: its overall score varied by 0.066. That is larger than every gain I measured, so none of the comparisons below can be read as a real improvement.

  1. 01

    Query rewrite helped some queries and hurt others

    It helped some colloquial Korean queries: for "커밋로그 보는 방법" ("how to view the commit log"), the git-log section moved to rank 1. Other queries got worse, the overall gain was not significant (p = 0.57), and faithfulness fell from 0.995 to 0.957. This eval ran on the chunked index, not the app's block index.

  2. 02

    Chunk size barely mattered

    Across chunk sizes from 300 to 1000, the overall score spread was 0.015, far inside the baseline's variation. 500 stays as a default, not as a proven optimum.

  3. 03

    Smaller images were cheaper, not better

    Adaptive image resizing cut input tokens by 8% and cost by 4%, but it was no faster and JSON parse success dropped on code screenshots.

limitations

  • Small n: 10 documents and 31 questions.
  • Single runs per configuration, while the baseline alone varied by 0.066 across rounds.
  • No human labels beyond 7 tagged queries.
  • The VLM model comparison was not run.
  • Edge cases are documented but mostly unhandled.
